# 性能优化五大类进展

本表按阶段验收更新；“本阶段完成”不表示该类别所有性能问题已解决。
当前阶段“减少重复认证并保留首次完整诊断基线”已完成验收。实验默认关闭，无新增固定防抖。
详见[阶段报告](method-body-certification-evaluation.md)及[开关契约](../features/method-body-certification.md)。
前阶段的[证书续期报告](method-certificate-renewal-evaluation.md)保留作为历史对照。

| 大类 | 已实施的基础及本阶段增量 | 仍待完成的工作 |
| --- | --- | --- |
| 1. 响应调度与卡顿控制 | 过期请求取消、token 解析检查、私有候选后台回收、发布前版本检查；本阶段将首次局部诊断认证延至实际需要诊断时，过期通知只同步文本并保留原始基线 | 完整语义和模型构建仍有不可中断段，原生回退仍有长尾；继续补齐前台 owner 解析的取消传递 |
| 2. 认证与依赖校验降耗 | 64 次编辑窗口续期；本阶段拆分便宜上下文检查与最终完整输入证明，查询构造和惰性绑定不再重复全量读盘；保留一个已完成的原生诊断基线，在最新诊断需要时认证 | 首次源见证构造、完整目录/磁盘内容核对、首次局部诊断对照及外围诊断格式化仍占时间；尚未缓存每次发布的成功证明 |
| 3. 扩大局部更新能力 | 函数/任务体查询、悬停、局部声明/类型/语句变化和合格类方法的局部诊断；首次连续编辑不再仅因过期通知清掉完整诊断标记而失去资格 | 后续宏展开受行数变化影响、新增外部引用、特殊化/驱动/时序及跨函数/文件依赖变化仍会原生回退；未实现所有方法体修改的局部诊断 |
| 4. 缓存生命周期与内存 | 稳定 UVM/package/module/层次复用、预算回退、协作式回收、固定原始 owner 与无历史句柄；本阶段最多保留一个待认证基线及一份目标文件文本，成功认证/失败回退/上下文回收按规则释放 | SourceManager 存储仍随输入增长，硬回收仍可能卡顿，私有候选与旧 owner 重叠会增加峰值；绑定语义缓存仍限进程内 |
| 5. 真实工作负载验证与交付 | 持续沿用原始 CVA6＋完整验证环境、UVM＋整个 404 实例 DUT 冻结；分别验证首次单次、首次连续、暖态、千次输入、宏回退、完整诊断和公共查询 | 本阶段千次输入、独立内存/强制回收、42 个公共状态、完整测试和安装检查均通过，随 main 交付；后续继续回归并扩展更多设计 |

五类总体状态：第 1～4 类均是“已完成若干阶段、仍有明确待办”；第 5 类是“按阶段完成验收与交付，后续持续回归”。

本阶段实现了上次列出的两个切入点，收益有边界：不改变后续宏行号且保持外部引用集合的首次连续编辑，末次诊断三轮中位约 856→176 ms；短暖态末次悬停约 48→35 ms，诊断约 83→54 ms。历史多行前缀新增 get_name 引用的首次编辑仍需完整诊断，约 0.85 s。不能将这些结果表述为所有首次诊断均已到几十毫秒。

下一步建议仍以第 2 类为主：复用已完成原生诊断的可投影结果，减少首次认证时再次格式化全部外围诊断的约 124 ms 开销；合并初次建立源见证时重复的文件读取。随后推进第 3 类：以受影响邻接方法为单位处理行数变化带来的宏行号依赖，再研究新增外部引用的依赖闭包，逐项保留完整原生 oracle。第 1 类不可中断语义段与第 4 类回收峰值继续独立跟踪，不能用认证收益替代这两项验收。

本阶段千次输入查询 p50/p95 为 45.80/77.84→34.85/55.86 ms，候选 1,008 次全成功；末次单点悬停 46.16→62.02 ms、诊断 72.58→79.90 ms 的退化也保留。独立峰值 RSS 1539.56→1537.14 MiB，不据单次探针宣称内存下降已稳定。792 CTest、17 Python、43 transport、SDK 709 文件恢复、默认/外置 UVM 安装检查均通过。
